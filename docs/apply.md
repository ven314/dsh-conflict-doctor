# 修复引擎：从「只报告」到「改配置」

`conflict-doctor` 的默认行为是**只读**的：它扫描你的 profile，告诉你哪里有问题，**不会碰你的文件**。

修复引擎在这条线上的位置，以及它现在能做什么、不能做什么。

## 三种输出，三种风险

| 命令                              | 做什么                                                             | 碰不碰盘                       |
| --------------------------------- | ------------------------------------------------------------------ | ------------------------------ |
| `conflict-doctor`                 | 只报告                                                             | 不碰                           |
| `conflict-doctor --dry-run`       | 在**内存**里套用每条修复，重跑一遍检测，告诉你修完之后结论会怎么变 | 不碰                           |
| `conflict-doctor --fix-out <dir>` | 把每条可应用的修复写成独立的 `.patch.yml` 文件到 `<dir>`           | **只写 `<dir>`，不动 profile** |
| `conflict-doctor --apply`         | **尚未实现**（见下）                                               | —                              |

## `--dry-run`：修之前先问「修完会怎样」

它不会真的改文件，而是把修复套用到内存里的副本上，再跑一遍完整检测，输出一张**修改前 → 修改后**的差异表。

这张表有三类结果，**不要混为一谈**：

- **✅ 已解决** —— 目标结论消失了，也没有引入新结论。这条修复是真的能解决问题的。
- **ℹ️ 仅建议（不消除结论）** —— 修完之后结论**还在**，但这是**正常的**，不是修复坏了。
  例如 `row-config-replaced`：同一行配置被多层重述是 DSH 的既定契约（每个 mode bundle 重述自己的完整配置），
  修复的目的是「让最后一层成为权威」，而不是消除重述。套用后结论仍在，正是预期行为。
- **❌ 未解决** —— 预期应该消除的结论没消除。**这才是真问题**，说明这条修复没有解决问题，别用它。

## `--fix-out`：拿到可挑可改的修复文件

`--fix-out ./fixes` 会写出：

```
profile-row-config-replaced.patch.yml      ← 一条修复
profile-row-config-replaced-2.patch.yml    ← 另一条（同 code 的修复各自独立）
README.md                                  ← 清单
```

两个关键点：

1. **这些文件不会被 DSH 加载。** `cordis.patch.yml` 旁边的 `.patch.yml` 是惰性的，放在哪里都不影响现有行为。
   **挑错了不会弄坏任何东西**——你可以放心地读、挑、改。
2. **清单里说明了每条修复的风险等级**：`safe`（纯新增行）、`caution`（改 config）、`destructive`（停用或删除行，会改变实际加载的内容）。
   拿到文件后请逐条判断，不要照抄。

## 在不信任本工具时，如何手动核对

如果你不想让工具碰你的文件，或者想确认一条修复到底改了什么：

1. `--fix-out ./fixes` 拿到文件。
2. 打开 `README.md`，它会列出每条修复改了哪一行、风险等级、为什么。
3. 打开 `.patch.yml`，它就是一段 patch 文档——**你可以自己读**，也可以拿去和 `cordis.patch.yml` 逐行比对。
4. 确认之后，把选中的行手动并入 `cordis.patch.yml`。

`--apply` 本质上就是把这一步自动化了，**并加上备份和回滚**。如果你不信任自动化的那一步，手动做完全可行。

## `--apply`：为什么现在还没有

安全原语已经全部就位，但**没有接到任何 CLI 开关上**：

- **路径闸**：目标文件必须在 profile 目录内，`node_modules` 一律拒绝（含前缀陷阱：`foo/node_modules` 不是 `node_modules` 的子目录）。
- **备份**：写之前把原文件备份为 `<file>.bak-<timestamp>`。
- **原子写**：写临时文件 + rename，失败不留半个文件。
- **回滚**：从备份逐字节还原。

开启 `--apply` 之前还需要：`--rollback` 命令、非 TTY 强制 `--yes`、全链路集成测试。这些做完之前**不会**写入任何 profile——目前全部能力仍是只读的。

## 一句话

> `--dry-run` 让你**看到**修复能不能解决问题，`--fix-out` 让你**拿到**修复自己挑，`--apply` 让工具**替你改**——这三者是递进的，前两者的存在本身就是为了让第三者可以被信任。
