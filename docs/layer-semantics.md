# 补丁层语义：整段替换、`!!js` 与键级溯源

这份文档说明 DSH patch 层的合并语义，以及审计在**不运行用户代码**的前提下能判定到哪一步。

## 一、层的应用顺序

profile 组合由若干层依序叠加而成，实测（本机 profile，12 层）：

```
[0]  bundle @deepseek-ai/dsh-base@0.1.0-rc.6
[1]  bundle @deepseek-ai/dsh-web-app@0.1.0-rc.6
[2]  bundle dshmarket@1.66.21
...
[11] user patch            ← 永远最后生效
```

每层是一个 YAML 数组，元素分两类：

| 形式                              | 含义                 |
| --------------------------------- | -------------------- |
| `- insert: [...]`                 | 插入新行             |
| `- id: X` + `config` / `disabled` | 按 id 改写已插入的行 |

**语义是整段替换，不是深合并。** 后一层的 `config` 整个盖掉前一层的，所以「最后一层胜出」。
本机实测：138 条 insert、36 条 override，最终台账 140 行、其中 24 行停用。

## 二、受影响的实例（本机真实数据）

47 行带 config，其中只有 **4 行**跨层重述，且**没有一层丢键**：

| row                    | 变化                                                              | 判定                      |
| ---------------------- | ----------------------------------------------------------------- | ------------------------- |
| `system-prompt`        | `persona`：`""` → 真实 prompt（最终层是第 1 层，不是 user patch） | info，值变化              |
| `agent-default-model`  | `provider`、`model` 值变化；新增 `reasoningEffort`                | info，值变化 + 新增       |
| `permission`           | 新增 `defaultPreset`；`presets` 值相同                            | info，纯新增              |
| `session-query-sqlite` | 两层 JSON 逐字节相同                                              | **不报**（仅键序/无变化） |

这就是为什么 `profile/row-config-replaced` 默认是 `info`：真数据里它全是良性的。
**只有当某一层写下的键被后续层丢弃时**才升级为 `warning`——那才是「配置明明写了却无效」的形态。
本机该情况为 0 次。

### 键序不算变化

`JSON.stringify` 对键序敏感，所以「键序不同」曾被误判为变化，然后产出一条证据写着「无差异」的结论——
**报了却说自己什么都没发现**。现在由逐键 diff 决定：可比较且完全无差异就不产生结论。

## 三、`!!js`：能判定的判定，不能判定的说清楚

patch 层可以写 `!!js <表达式>` 代替字面量。求值等于在审计里执行用户代码，本工具**拒绝**这么做。
但「不求值」不等于「中立」：早期实现把所有 `!!js` 当成键不存在，并声称「按未停用处理」。

### 那个默认值是错的

本机 profile（Windows）里有：

```yaml
- id: bash-sandbox
  disabled: !!js process.platform === 'win32'
```

这些行**确实是停用的**，而审计以为它们启用。`record.disabled === true` 对字符串永远为假，
所以**每一个条件停用都被静默读成启用**。当时没有任何检测器依赖这个基线，正因如此它一直没被发现——
一个没人问的错误事实，仍然会污染此后所有建立在它之上的存在性判断。

### 白名单解释器

`src/expr.ts` 实现了一个极小的解释器。支持：

- 字面量：字符串、数字、`true`/`false`/`null`
- `process.platform` / `process.arch` / `process.version`
- `===` `!==` `==` `!=`、`!`、`&&`、`||`、`??`、括号

**明确拒绝**（返回 `undefined`，调用方必须当作「假设默认」，绝不能当作 false）：
属性链、函数调用、模板字符串、`new`/`require`/`import`/`eval`、`process.env.*`、`process.cwd()`、
`dshHomePath(...)`、`ctx.*`。

本机 17 个不同表达式：**5 个判定**（平台比较与字面量默认值），**12 个拒绝**。
覆盖率说明现在报这个拆分，而不是过去那句「一律不求值」——正是那句笼统的话让错误的基线一直是隐形的。

判定 `disabled` 的三种结果，区别很重要：

| 情况                  | 结果                                                   |
| --------------------- | ------------------------------------------------------ |
| 字面量 `true`/`false` | 已判定                                                 |
| `!!js` 在白名单内     | 已判定（真实求值）                                     |
| `!!js` 超出白名单     | **未判定**：按默认启用处理，但记录 `disabledUndecided` |

下游行为对「判定为 false」和「假设为 false」是一样的；区别只在于**后者需要披露**。

## 四、inject 图与环

patch 行可以声明 `inject: [webStartup]`。本机有 3 条真实边：

```
webserver    → webStartup
web-runtime  → webStartup
connection   → webRuntime
```

`profile/inject-cycle` 只依据这些边找环：环上每一行都在等另一行，因此整条链永远无法激活。
**这个结论不需要知道「谁提供什么」**，所以它不会被提供方识别的不确定性污染。本机无环。

## 五、**没有**实现的两件事

### 1. 静态「inject 无人提供」

证据是决定性的。本机 Web UI 正常工作（127.0.0.1:19387），所以 `webStartup` **确实被提供**；
但 `@deepseek-ai/dsh-web-app` 里找不到任何字面量 `super(ctx, 'name')` 供扫描器识别——
而 `dsh-web`（`web`）和 `dsh-host-webserver`（`webServer`）是能被识别的。

**字面量扫描在这里被证明是盲的。** 因此「没有声明」推不出「没有服务」，
照这个写会在这个健康 profile 上报出 **3 条误报**。
它所瞄准的真实故障已由 `live/pending-missing-service` 覆盖——那个检测器读的是真实注册表，不是猜。

### 2. 与 `dsh --dump-config` 对比（W6-12）

`dsh --dump-config` 在本机**根本跑不起来**：npm 版 CLI 解析不到 experimental bundle，
报 `cannot resolve profile bundle "@deepseek-ai/dsh-experimental-agent-team-profile"`。
这本身就是 W1 那条发现的复述：npm 版与打包桌面版用的不是同一套 bundle 来源。
因此台账无法与官方 dump 做逐行 diff；它的正确性改由「插入 138 + 覆盖 36 依序套用」的规则与逐条核对支撑。

### 另外：group 嵌套（W6-11）

12 个真实层文件里 `group: true` 出现 **0 次**，且 `dsh.*` 清单词表里没有 group 字段。
没有数据可验证的实现不做。

## 六、测试覆盖

| 检查  | 内容                                                                                                                                                                    |
| ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H1–H5 | `!!js` 解释器：平台比较随注入环境变化、字面量与默认值惯用法、**拒绝一切真实代码**、值不得被当作条件、真实 profile 报出判定/拒绝拆分                                     |
| I1–I7 | 键级溯源：丢键升级为 warning、值变化保留双向值、纯新增不误报为丢失、逐字节相同的重述不报、**仅键序不同不算变化**、非对象 config 如实降级、真实 profile 每条都带键级证据 |
| J1–J5 | inject 环：二元环与传递环带路径报出、链与扇出（真实形态）保持静默、提供方不在行内时不猜、真实 profile 可提取 3 条边且无环                                               |

H3 是最值钱的一条：它把「不许求值真实代码」钉成了测试，包括 `eval`、`require`、模板字符串、
立即执行函数。I5 次之：它钉住的是「报了却承认什么都没发现」这种自相矛盾的噪音。
